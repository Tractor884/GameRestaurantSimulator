# DESIGN-CONCEPT-TZ — Визуальный редизайн игры (master-ТЗ)

> **Источник:** «Внедрение визуала.docx» (upload/), перенесён в проект дословно.
> **Статус:** утверждён пользователем как полное ТЗ визуального слоя.
> **Связанные документы:** `PROJECT-PASSPORT.md` (как устроена игра), `worklog.md` (что уже делалось).
> **Производные документы (этап 1):** `ART_STYLE.md`, `CHARACTER_BIBLE.md`, `VISUAL_STATE_MAP.md`, `ASSET_LIST.md`, `PRESENTATION-LAYER.md`.

---

Это master-документ, который задаёт архитектуру редизайна: что рисовать, как связывать изображения с KPI, какие персонажи нужны и как графика должна подключаться к существующему движку.

Я бы использовал его в несколько этапов. Так вы не рискуете сломать уже работающую игру.

## Что вы получите в итоге

В конечном состоянии ваш существующий проект останется той же игрой с тем же экономическим движком, но поверх него появится новый визуальный слой.

Условно сейчас архитектура выглядит так:

```
Экономический движок
    ↓
GameState
    ↓
Текущие UI-экраны
```

После редизайна:

```
Экономический движок
    ↓
GameState
    ↓
Visual / Presentation Layer
    ↓
Мультяшный интерфейс
    ↓
Персонажи + сцены + предметы + KPI
```

То есть, например, движок уже рассчитывает:

```
fatigue = 76
morale = 43
staffRisk = 58
```

Новый слой интерпретирует это:

```
HR = concerned
waiter = exhausted
cook = tired
show_resignation = false
team_state = warning
```

И интерфейс показывает нужные статичные изображения.

Экономика при этом не меняется.

## Что именно появится в проекте

В результате полной работы я ожидаю пять групп новых материалов.

### 1. Дизайн-документация

Например:

- `ART_STYLE.md`
- `CHARACTER_BIBLE.md`
- `VISUAL_STATE_MAP.md`

В них будет окончательно зафиксировано:

## Очень важный момент

**Не нужно создавать второй проект.**

Графику нужно подключить непосредственно к существующему проекту.

Сейчас у вас уже есть единая страница /, 15 внутренних экранов, Zustand-store и независимый headless-движок. Именно поэтому визуальный слой можно добавить сверху, не меняя экономическую архитектуру.

## Как пользоваться ТЗ практически

### Этап 1. Добавить ТЗ внутрь проекта

Создать в корне проекта файл `DESIGN-CONCEPT-TZ.md` и вставить туда всё ТЗ. Рядом уже находятся `PROJECT-PASSPORT.md`, `worklog.md`. Тогда любая нейросеть-разработчик получает одновременно:

- **PROJECT-PASSPORT** → как сейчас устроена игра;
- **worklog** → что уже делалось и какие ошибки нельзя повторять;
- **DESIGN-CONCEPT-TZ** → как именно нужно изменить графическую часть.

### Что дать нейросети первым запросом

Не нужно говорить «Реализуй всё ТЗ» — это слишком большая задача.

Первый запрос должен быть примерно таким:

> В проекте находятся три обязательных документа: PROJECT-PASSPORT.md, worklog.md, DESIGN-CONCEPT-TZ.md. Сначала внимательно прочитай все три. Экономический движок, формулы, баланс и существующие функции изменять запрещено. Сейчас выполняем только проектировочную фазу графического редизайна. Подготовь:
> 1. ART_STYLE.md;
> 2. CHARACTER_BIBLE.md;
> 3. VISUAL_STATE_MAP.md;
> 4. ASSET_LIST.md;
> 5. предложение по архитектуре presentation layer.
>
> Код экранов пока не менять. Графические ассеты массово не создавать. После выполнения остановись и покажи мне результат на согласование.

Это правильный первый шаг.

**Почему нельзя сразу просить переделать все экраны:** нейросеть начнёт принимать десятки дизайнерских решений самостоятельно (какой стиль лиц; как выглядит бухгалтер; куда поставить персонажа; насколько большая иллюстрация; где проходит граница warning/critical; какие ассеты повторно используются). После 15 экранов исправлять это будет очень дорого. Сначала нужно утвердить **систему**.

### Этап 2. Утвердить персонажей

После первой фазы должна появиться таблица вида:

| Персонаж | Роль | Great | Normal | Warning | Critical |
|---|---|---|---|---|---|
| Анна | HR | довольна | спокойна | обеспокоена | серьёзная |
| Максим | шеф | горд | работает | недоволен | раздражён |
| Ирина | бухгалтер | спокойна | нейтральна | тревожится | кризис |
| Сергей | кладовщик | порядок | работа | дефицит | хаос |

Тогда уже можно создавать изображения.

### Этап 3. Сначала сделать только 5 экранов

Первый пилот:

1. Главный.
2. Персонал.
3. Склад.
4. Финансы.
5. Оборудование.

Почему именно они? Здесь можно проверить почти весь визуальный язык: люди; настроение; предметы; грязь; склад; деньги; техника; композитные сцены.

Если эти пять выглядят хорошо, оставшиеся десять уже значительно проще.

## Как создавать сами изображения

**Вариант А — нейросеть-разработчик умеет генерировать изображения.** Тогда она получает CHARACTER_BIBLE.md и ASSET_LIST.md и создаёт ассеты последовательно. Но всё равно не стоит говорить «сгенерируй сразу 200 картинок». Сначала: HR; бухгалтер; кладовщик; техник; основная сцена ресторана. И утверждаем стиль.

**Вариант Б — код делает одна нейросеть, изображения другая.** Разработчик создаёт visualState, CharacterPanel, RestaurantScene, asset registry; изображения создаются отдельно и просто кладутся в `/public/game-art/`. Никакого изменения движка для этого не требуется.

### Пример подключения изображения

Допустим, у нас есть `public/game-art/characters/hr/hr_warning.webp`.

В asset registry:

```ts
export const CHARACTERS = {
  hr: {
    great: "/game-art/characters/hr/hr_great.webp",
    normal: "/game-art/characters/hr/hr_normal.webp",
    warning: "/game-art/characters/hr/hr_warning.webp",
    critical: "/game-art/characters/hr/hr_critical.webp",
  },
}
```

Дальше visual logic:

```ts
function getHrState(state: GameState) {
  const fatigue = averageFatigue(state);
  const morale = averageMorale(state);
  if (fatigue > 80 || morale < 30) return "critical";
  if (fatigue > 60 || morale < 50) return "warning";
  if (fatigue < 30 && morale > 75) return "great";
  return "normal";
}
```

Важно: реальные формулы потом нужно настроить аккуратнее и централизованно.

А экран просто получает:

```tsx
<CharacterPortrait src={CHARACTERS.hr[visualState.hrMood]} />
```

И всё. Экономическая система при этом ничего не знает о картинке HR.

### Как сделать грязь на полу

Базовая сцена: `restaurant_base.webp`. Отдельный прозрачный слой: `floor_dirty.webp`.

Если `cleanliness < threshold` — рендерим сверху `<SceneLayer src="/game-art/objects/floor_dirty.webp" />`.

Если чистота хорошая — слой вообще не показывается.

### Как сделать очередь

Отдельные слои: `queue_small.webp`, `queue_medium.webp`, `queue_large.webp`.

- Queue 0–2 → ничего
- Queue 3–5 → small
- Queue 6–10 → medium
- Queue >10 → large

Точные значения потом привяжем к текущей модели очереди.

### Сломанная кофемашина

`coffee_normal`, `coffee_warning`, `coffee_broken`. Display-state выводится из: wear; technical risk; активного технического события.

Сломанная машина появляется **не случайно**, а потому что движок говорит, что с техникой проблема. Это принципиально.

### Испорченные продукты

Данные уже существуют: expired; near expiry; waste; stock level. Из них presentation layer выбирает: balanced / low_stock / overstock / near_expiry / spoiled — и показывает нужные ассеты.

## Как будет выглядеть главный экран технически

```tsx
<RestaurantScene>
  <BaseRestaurant />
  <Entrance state={visual.queue} />
  <Guests state={visual.guestMood} />
  <Staff state={visual.staffState} />
  <Cleanliness state={visual.cleanliness} />
  <Dishwashing state={visual.dishes} />
  <CoffeeMachine state={visual.coffeeMachine} />
</RestaurantScene>
```

Все изображения статичны. Но из-за комбинаций сцена будет выглядеть живой.

**Это даст огромное количество комбинаций.** Например всего 6 независимых признаков по 3 состояния: 3 × 3 × 3 × 3 × 3 × 3 = 729 визуальных комбинаций. Но не нужно рисовать 729 ресторанов — нужно нарисовать около 18 слоёв. Это одна из главных причин, почему рекомендована композитная система.

## Как дополнять проект графикой постепенно

Сначала: HR, бухгалтер, кладовщик, техник. Потом: маркетолог, банкир, владелец.

Игра не должна зависеть от того, готова ли вся графика. Для отсутствующего ассета можно использовать fallback: `character_normal`.

Таким образом графический редизайн можно внедрять постепенно.

## Какой результат считается правильным после первого этапа

**Главный экран** — уже новая сцена ресторана: очередь; настроение гостей; чистота; перегруженная кухня; состояние техники.

**Персонал** — есть HR. Она реагирует на fatigue; morale; staffing.

**Склад** — кладовщик + визуальное состояние запасов.

**Финансы** — бухгалтер + состояние кассы.

**Оборудование** — техник + состояние техники.

И остальные функции игры по-прежнему работают как раньше.

### После этого надо обязательно сравнить экономику

Берём одинаковый seed, initial state, decisions — и прогоняем игру до и после редизайна. Результат должен быть одинаковым: Revenue, Food Cost, Labor Cost, Cash, Rating, BSC.

Потому что новый визуальный слой не должен влиять на движок.
